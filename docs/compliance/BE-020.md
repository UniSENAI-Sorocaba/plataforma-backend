# BE-020 — política de cobertura

Os thresholds versionados no bloco `be020.coverage.*` do `pom.xml` seguem a POL-QA-001: backend com LINE >= 80% e BRANCH >= 70%; cada pacote crítico selecionado com LINE >= 90% e BRANCH >= 80%. Não há exclusões de classes.

## Pacotes críticos

O JaCoCo executa um único gate crítico por elemento `PACKAGE`. As seleções são disjuntas: cada classe entra em no máximo um grupo; o limite é avaliado em cada pacote incluído, sem agregar pacotes de uma categoria para compensar outro pacote abaixo do mínimo.

| Domínio | Propriedade de seleção no POM | Critério |
| --- | --- | --- |
| Autenticação | `be020.coverage.critical.auth.include` (`plataforma/auth/**`) | Hash e configuração de senha, tokens e recuperação de acesso. |
| Autorização — API | `be020.coverage.critical.authorization.api.include` (`br/senai/plataformadigital/auth/api/authorization/**`) | Decisões e políticas de autorização. |
| Autorização — web | `be020.coverage.critical.authorization.web.include` (`br/senai/plataformadigital/auth/web/**`) | Interceptor, configuração e rotas que aplicam autorização. |
| Segurança | `be020.coverage.critical.security.include` (`plataforma/security/**`) | Redação de segredos, masking em logs e filtragem de métricas. |
| Regras core — serviços | `be020.coverage.critical.core.service.include` (`plataforma/service/**`) | Operações e regras de domínio usadas pelos serviços de backend. |
| Regras core — modelos | `be020.coverage.critical.core.model.include` (`plataforma/model/**`) | Estados, papéis e entidades que representam regras/transições do domínio. |
| Regras core — impacto | `be020.coverage.critical.core.impact.include` (`br/senai/plataformadigital/portal/impact/**`) | Ciclo de vida e publicação de conteúdo de impacto, preservando o gate 90/80 que já existia. |
| Regras core — configuração de impacto | `be020.coverage.critical.core.impact.config.include` (`plataforma/config/ImpactConfiguration*`) | Configuração específica do domínio de impacto incluída no gate que já existia. |

Os seletores são propriedades Maven para facilitar revisão e expansão sem alterar as regras de contagem. A lista acompanha o mapeamento da Parte 1 e as categorias críticas da POL-QA-001. A inclusão de `impact` e `ImpactConfiguration` preserva a cobertura crítica já configurada para o domínio.

## Relatórios e falhas

- Relatório global LINE/BRANCH por pacote: `target/site/jacoco-backend/`.
- Relatório crítico HTML e XML: `target/site/jacoco-critical/`.
- O `critical-domain-coverage` verifica cada pacote incluído separadamente. Uma falha informa o nome do pacote, a métrica (lines/branches), a razão observada e o mínimo exigido.
- Os workflows Maven armazenam ambos os diretórios como artefatos de evidência.

O gate roda na fase Maven `verify` e usa `haltOnFailure=true`. Um comando local pode sobrescrever essa propriedade apenas para diagnóstico e geração de todos os relatórios; tal override não deve ser usado no CI.

## Check obrigatório de pull request

O workflow `.github/workflows/contracts.yml` expõe o job estável `coverage-gate` em pull requests com base `develop` ou `main`. Ele executa `mvn clean verify` (unitários, integração e JaCoCo), testes de contrato e compatibilidade OpenAPI; os checks Maven mantêm `haltOnFailure=true`. O workflow também falha explicitamente se os relatórios Surefire ou o resumo TAP estiverem ausentes, ou se qualquer teste estiver marcado como skipped.

Os relatórios HTML/XML e o resumo por módulo/pacote são preservados mesmo após falha do build, usando os dados JaCoCo disponíveis. Se a compilação terminar antes de produzir dados, o resumo registra que a cobertura está indisponível; o job permanece reprovado pelo passo que falhou.

Em 2026-11-19, o check `coverage-gate` foi configurado como obrigatório nas regras de proteção de `develop` e `main`, com exigência de branch atualizada (`strict`) e aplicação também a administradores. Para revisar futuramente: **Settings > Branches > Branch protection rule > Require status checks > `coverage-gate`**.

O job separado `Spec compliance` depende do secret `GOVERNANCE_READ_TOKEN` para consultar o repositório privado de governança. No PR #48, a execução confirmou que o secret não está disponível: o gate de cobertura passou, enquanto `Spec compliance` falhou por essa dependência. Configurar um token dedicado de leitura (Contents: read) como Actions secret continua necessário para esse job.
